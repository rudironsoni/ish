WAMR role

WAMR is not a replacement for iox’s Linux-like kernel substrate.
WAMR is a secondary execution backend used only for WASM/WASI images.

iox remains the single owner of:
- task and virtual process semantics
- file descriptor tables
- VFS, cwd, root, and mount behavior
- signals, PTY, TTY, job control
- `/proc` and `/dev`
- clocks, random, environment
- `fork`, `execve`, `_exit`, `wait*`

WAMR is responsible only for:
- loading and instantiating WASM modules
- managing WASM execution state and linear memory
- exposing WASI imports
- translating WASI calls into the shared iox kernel substrate

All WASI operations must resolve through the same iox kernel services used by native commands.
WAMR must not define a separate process, filesystem, or signal model.

What you must delete or replace

1. Delete `src/iox/core/iox_context.c` as a competing execution model.
   - salvage useful logic
   - migrate it into the canonical task model
   - do not preserve dual ownership

2. Delete the global FD ownership in `src/iox/core/iox_file.c`.
   - move FD ownership to `task->files`
   - remove global FD state as a source of truth

3. Replace passthrough ownership.
   - `iox_libc_delegate.c` and similar passthrough layers must stop owning semantics
   - libc may still be used as a low-level host mechanism where needed
   - policy and semantics must belong to iox kernel subsystems, not delegate wrappers

Deterministic execution model

You must implement `execve` as virtual image replacement inside iox.

`execve` must resolve exactly one of these image types:

1. native registered command
2. WASM/WASI module
3. script with shebang

No other execution path is allowed in the core design.

`execve` success semantics inside iox:

1. the task keeps the same PID
2. the task keeps the same PGID
3. the task keeps the same SID
4. the task keeps the same controlling TTY
5. cwd and root are preserved
6. resource limits are preserved
7. `FD_CLOEXEC` descriptors are closed
8. argv and env are replaced
9. signal disposition is updated according to exec rules
10. control transfers to the resolved image runner

Native execution path

You must use a native command registry.

Examples:
- `/bin/bash`
- `/bin/sh`
- `/bin/ls`
- `/usr/bin/env`

These resolve to prelinked native entrypoints compiled into the app or linked artifacts.

Do not depend on constructor-only registration as the primary mechanism.
Use a robust explicit registry mechanism, preferably generated at build time.

Required native entry ABI:

`int iox_native_main(iox_task_t *task, int argc, char **argv, char **envp)`

WAMR execution path

WAMR must be integrated as a first-class execution backend using the same substrate as native code.

Mandatory rules:

1. WASI fd operations use the same `task->files`
2. WASI path operations use the same VFS and cwd and root
3. WASI stdio uses the same descriptors as native tasks
4. WASI clocks and random source go through the same iox kernel abstractions
5. WASI execution does not create a separate process universe
6. WAMR is not allowed to own independent process, fs, or signal semantics

Fork model

This is fixed.

Do not use real host `fork()`.

Implement iox `fork()` as a virtual process creation primitive inside the iox task system.

Rules:

1. parent and child are separate `iox_task` objects
2. each task has its own `files`, `fs`, `sighand`, `tty`, and `exec_image` state according to iox semantics
3. the child runs on a host thread owned by iox
4. all fork semantics are implemented by iox, not by the host kernel
5. user-visible behavior must aim to match Linux userland expectations closely enough for bash-class software

You are not allowed to evade this problem by redefining the goal.
You must design the subsystem to emulate the required process behavior inside iox.

Important restriction:
Do not propose vague continuation tricks such as `jmp_buf` without a full concrete mechanism.
Do not hand-wave child continuation.
Design the runtime model explicitly and concretely.
